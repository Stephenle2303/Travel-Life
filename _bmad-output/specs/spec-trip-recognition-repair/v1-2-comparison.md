## What changed, and what did not

- **Fixed:** Finding F1 (silent `NOT_TRIP` with empty reasons) — gone, 0
  silent drops. Finding F11 (screenshots/downloads bypassing provenance) —
  gone, S18b hidden with `non-capture-source` in both Home modes.
- **Fixed, found while wiring this benchmark:** `reconstruction-v1`'s 5 km
  place clustering already merges two points 3 km apart into one place, so
  checking "two places ≥1 km apart" by place id can never see them as
  distinct. v1.2 checks raw coordinates directly instead (one-line fix,
  [outcome-v1-2.ts](../../../apps/mobile/src/reconstruction/outcome-v1-2.ts)'s
  `hasTwoSeparatedPlaces`). See the error playbook entry dated 2026-11-19.
- **Confirmed, not changed:** v1.1's code (`engine.ts`, `engine-v1-1.ts`,
  `canonical-core.ts`, `canonical-projection.ts`, `candidate-projection.ts`)
  has zero diff in this change; `qualifyGraphJourneyV11` stays exported and
  callable, so selecting it again reproduces the v1.1 column exactly
  (CAP-8's rollback requirement, verified structurally rather than by a
  redundant runtime test).
- **Not yet consolidated (CAP-7 remaining):** the Possible-trips UI still
  reads `candidate-projection.ts`'s separate `recognizable-travel-shadow-v1`
  policy, not v1.2's `SUGGESTED` classification. v1.2's outcome is written to
  `reconstruction_trip_qualification` (CAP-2/CAP-3 satisfied at the
  authoritative table) but the two Possible-trips feeds are not yet merged.
  See [consolidation.md](consolidation.md)'s updated status.
- **Reviewed and fixed, same result:** a `/code-review high` pass after this
  table was first produced found 9 real bugs in the implementation (self-
  counting frequent-place matches, a vacuous Home-coverage check, an
  inverted duplicate-family tie-break, two lingering v1.1 call sites, and a
  real O(journeys × library) scaling cost, among others — see the error
  playbook, 2026-11-19). All were fixed; this benchmark was rerun after each
  fix and still shows 54/54, 0 silent drops, 0 false Atlas trips — none of
  the fixes changed any scenario's outcome, because none of the bugs were
  exercised by this specific scenario set (they needed shapes — duplicate
  families, missing capture days, >=8 prior visits, self-referential
  journey markers — this benchmark doesn't yet generate). That gap is itself
  worth closing in a future increment of M10.1.
- **Not yet covered by this benchmark:** S15 (a pure GPS-less window has no
  visit/journey at all under the unchanged v1 engine, so `qualifyGraphJourneyV12`
  never sees it; the `no-location` reason is proven at the unit level instead,
  `reconstruction-outcome-v1-2.test.ts`), S17 (no GPS-jump contradiction
  detector exists anywhere in the codebase yet to generate a genuine
  `timeConflict`; proven at the unit level only), S20 (correction survival is
  unchanged by construction — the `ownerConfirmed`/rejected shortcuts and
  `confirmedJourneyIds` short-circuit in `repository.ts` were not touched;
  covered by the existing correction test suite plus the owner-confirmed/
  rejected unit tests here).
