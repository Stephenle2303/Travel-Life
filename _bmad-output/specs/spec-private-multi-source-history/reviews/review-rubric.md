# Good-spine rubric review

Reviewed 2026-10-28 against the architecture spine, all sibling companions (including SPEC and memlog), canonical M6-M9 backlog, AGENTS.md and diagnostic policy. Source spot-check confirmed native reconstruction engine/repository boundaries and existing maintenance task/scheduler. This is a document review; no runtime or service acceptance was performed.

**Verdict: revise before finalization.** The core ownership, correction, privacy and activation decisions are strong, but three shared M6-M7 seams remain unspecified enough for independently built stories to disagree.

## High findings

1. **M6 snapshot acceptance and pending contributions have no explicit protocol state.** AD-4 and sync-contract's push/restore describe a journal feeding the canonical aggregate, while canonical AC-M6.3-3 requires a different local record to remain a separate pending contribution until M7 merging exists. M6.4 must already restore the acknowledged history, although the canonical worker is introduced in M7.3. Neither the spine nor experience companion distinguishes the accepted first snapshot, a subsequent pending contribution and the later merged aggregate. Builders can accidentally activate a second source early or make M6 restore depend on unfinished M7 machinery. **Disposition: autofix.** Add a shared invariant and short lifecycle: the first compatible consented snapshot may become the M6 restore authority; subsequent distinct contributions remain acknowledged but inactive/pending; only the M7 canonical build may atomically promote the combined result. Preserve separate revision namespaces or explicitly distinguish receipt, snapshot and active aggregate revisions. Cover attach-existing-account and M6-only restore fixtures.

2. **Durable client outbox and scheduler ownership are absent.** The contract describes server receipts, bounded batches, timeouts and worker retries, but no durable mutation/outbox checkpoint or shared coordinator between foreground actions and native background jobs. Canonical AC-M7.1-2 and -4 require restart-safe outboxes, independently progressing cursors and foreground catch-up when platform scheduling is denied/delayed. Existing maintenance task/scheduler code makes this a brownfield integration seam, not a new service detail. A page could otherwise be reconstructed with a new mutation ID after restart, or foreground and background writers could race local checkpoint activation. **Disposition: autofix.** Bind both execution paths to one account/source/generation-scoped durable queue and checkpoint protocol, persist mutation identity before send, serialize/lease overlapping claims, checkpoint only acknowledged work, and check session/consent fences on resume. Declare platform-permitted background scheduling plus foreground catch-up; name native adapters as owners without choosing story-level implementation classes.

3. **Removal authorization promises need a signed-URL and cache boundary.** AD-8 denies stale readers, AD-7 makes URLs transient, and sync-contract permits five-minute signed URLs with live checks only at issuance. An already issued bearer URL can survive a session/source fence until expiry unless another serving mechanism checks access. Offline cached derivatives also cannot be remotely erased immediately. The experience companion mentions offline-device limitations, but does not state the guarantee for issued capabilities versus subsequent API access or renderer activation. **Disposition: autofix.** Declare bounded residual URL access explicitly or require access-time mediation where immediate denial is required; define foreground cache hiding/purging on observed fences and final render/export revalidation. Test issuance-before-revocation, stale render completion and offline reconnect separately. Do not claim immediate global byte revocation.

## Medium findings

4. **The offline-replica authorization state is ambiguous.** The backlog requires cached restored history to be readable offline (AC-M6.4-3), whereas the contract requires live auth for protected server actions and the experience says account context is unavailable when session blocked. Define when a previously accepted account session may read its scoped offline replica without a network refresh, and what happens on expired refresh, explicit local signout, account switch or an observed fence. Otherwise auth and UI builders can independently require online access or expose a locally blocked account. **Disposition: autofix; no product reconsideration is required.**

5. **No explicit M6-M7 story ownership map for shared substrate gates.** Exact DTO derivation before M6.3 is correctly deferred to that story, but live-session fences, the initial restore artifact and canonical-core extraction need named introduction points so earlier stories remain independently complete. **Disposition: autofix** with a small prerequisite/owner table; retain detailed per-story diagnostic maps as implementation gates rather than fabricating source functions now.

## Rubric assessment

- **Real divergence points:** ownership contexts, isolated auth clients, wire identities, server authority, mutation receipts, CAS activation, duplicate support and correction conflicts are directly addressed. Findings 1-2 are the major missing cross-story decisions.
- **Enforceable AD rules:** Binds/Prevents/Rule structure is consistent; AD-3 through AD-6 support objective schema, equivalence, idempotency and conflict tests. AD-8 needs the guarantee clarification above. AD-9 appropriately treats operational readiness as an enablement gate.
- **Dimensions:** persistence, security, media, operations and provider separation are covered. Native background scheduling/foreground recovery is the missing operational dimension.
- **Preservation and capability coverage:** CAP-1 through CAP-8 retain approved scope, reviewed facts, Hide/Exclude, manual history, committed Replay/audio, local continuity and disabled hosted publication. Pending-contribution staging needs explicit representation to preserve the M6/M7 delivery boundary.
- **Brownfield fit:** retaining Expo/SQLite/Supabase and extracting the existing canonical functions fits the repository; no greenfield algorithm is introduced. Shared schema derivation and typed lineage remapping remain deliberate pre-code gates. Installed package claims were not independently exhaustively audited in this rubric pass.
- **Deferred decisions:** provider-specific M8/M9 scopes/jobs and actual production retention settings can remain deferred because common protocol/authorization constraints bind them. The M6 snapshot and M7 queue contracts cannot safely be deferred independently to their stories.
- **Verification honesty:** companions distinguish synthetic/host evidence from physical and deployed acceptance. Runtime diagnostic maps are explicitly required before each implementation; this documentation-only review adds no runtime events. The listed external references/research claims were not independently revalidated here.

No code or specification files were changed by this review. Findings are omissions/ambiguities in a draft, not observed runtime incidents.
