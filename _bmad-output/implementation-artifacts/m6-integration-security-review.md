# M6 integration security review

Reviewed 2026-10-28, read-only source inspection of history contract/native/store/transfer/service, record context/provider/panel and both M6 SQL migrations. No deployment, private evidence, runtime acceptance or production fix is established. The concurrent M7 migration was empty when inspected and is outside this verdict.

## Actionable findings

1. **P1 — Reject device-local media handles on restore, not only on export.** `history-contract.ts:38` accepts any object/array in JSON fields. `portableReplayJson:49` removes preparedArtifact and custom soundtrack localUri only during export; incoming replay JSON is inserted verbatim by stageAccountReplica. Existing reconstruction repository parses preparedArtifact and custom soundtrack.localUri as trusted local playback/cache inputs. A validly shaped account page can therefore inject local file/cache references on the receiving device rather than resolve authorized account media. Define an exact portable Replay DTO, reject local handles and unknown fields on both SQL ingestion and native restore, and test malicious preparedArtifact/custom file URI payloads before activation. The account preview adapter returning unavailable does not by itself fence soundtrack/cache paths.

2. **P1 — Local replica access does not honor observed account/source deletion.** `record-context.ts:25-30` activates any persisted owner replica when the email identity matches. `history-service.ts:30-35` learns deleted status or missing active snapshot but does not invalidate the replica pointer or selected context. SQL delete-account/source removal clears server content, while loadReplica/openAccount can subsequently expose an older local copy for the same signed-in owner. Fence replica selection by saved account/source generations and observed deletion, invalidate active context immediately, and explicitly define offline retained-cache behavior. Test deletion/status followed by openAccount and concurrent restore/pointer commit; do not rely on hiding one UI button.

3. **P2 — Paused/disconnected sources cannot subsequently be removed.** `20261028064937_m6_history_transfer_guards.sql:65-78` includes source-control behind `s.state <> 'active'` rejection. Pause/disconnect therefore prevents a later source-control removed request; the allowed mode list also offers no active/resume transition. Separate read/upload eligibility from control transitions and test active -> paused/disconnected -> removed (and an explicitly supported resume path). Account deletion still works, but should not be required to remove one source.

4. **P2 — Contract validation proves primitive layout, not the accepted semantic schema.** `history-contract.ts:27-44` and SQL valid_record accept fractional revisions, arbitrary date/action/state strings and arbitrary nested correction/privacy/Replay JSON. Some fail native constraints only after the server has activated the snapshot; others rely on downstream fallback behavior. For example a manual row with date_kind='invalid' passes both transfer validators and fails its native CHECK during restore. Validate enums, integer revisions, dates, JSON shapes and cross-record constraints before server activation; keep the prior account snapshot usable if validation fails. Include malformed privacy membership and Replay selections in rejection tests.

5. **P2 — Late context/pointer completion can override a later local choice or update the wrong screen state.** `record-context.ts:25-30` captures owner but no selection generation: openAccount awaiting loadReplica followed by local() still activates the account on completion. `history-service.ts:73-74` likewise awaits saveReplica then updates shared success state without a final current() check, so a late completion after signout/lock/new owner can overwrite the new owner's status. Use selection/action epochs at every completion and before durable pointer activation. Test held loadReplica/saveReplica across local(), signout and owner switch.

6. **P2 — Diagnostic mapping collapses schema/provider/native failures.** `history-service.ts:17` maps every non-HistoryTransferError to HISTORY_STORAGE, including HistoryContractError, native rebuild/schema failures and arbitrary programming exceptions. Restore uses one HISTORY_RESTORE stage across pull, native insertion/rebuild and pointer activation. This does not meet the diagnostic policy's exact boundary/classification requirement. Preserve typed schema errors, classify the known native boundaries separately, pass one correlation through transport/native/store, and assert exact fixed events for each injected fault. Unknown causes must remain UNKNOWN at the known stage.

## Positive controls observed

- Separate account replica database leaves the local history DB untouched; SQL statements use fixed layout identifiers and parameterized values.
- RPC derives subject/session from live Auth, checks non-anonymous verified identity, locks the account row, scopes queries by owner, revokes direct table access and fences deletion before cleanup.
- Account media adapter supplies no local photo URI; signout-driven provider remount and controller generation fences reduce stale UI exposure.
- Stable transfer request IDs and server digest receipts preserve retries; per-source snapshot revision CAS rejects competing source activation.

## Limits and next verification

These are source-derived findings, not reproduced device incidents. Root should add targeted regression evidence and real Postgres role/transaction tests before claiming acceptance; no query or private upload was performed here. Inspection commands twice passed Windows wildcard paths to rg; rg rejected them and subsequent searches used directory plus -g. This tooling failure did not change source or establish a product result and should be appended to the existing playbook tooling lesson by the owning integrator.
